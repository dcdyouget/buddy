# 自动上下文与用量日志

UI 继续调用 `ChatEngine::send_message_from_history`，用户无需选择话题。实现位于 `crates/engine/src/context`；低层 `send_message` 仍用于显式传入消息的集成调用，并执行相同的 30 条 / 50% 输入预算检查。

## 发送流程

1. 读取独立索引，先占用当前生成槽位，相关性检测期间也能取消。
2. 有历史时，使用当前选中模型和服务商进行独立的相关性请求。间隔不超过 5 分钟时查最近 10 → 20 → 30 条，超过时查 5 → 10 → 20 → 30 条；只有模型要求更多信息才扩展。时间不直接决定新话题。优先使用每轮摘要，摘要未就绪时读有界原文片段。窗口边缘允许用摘要表示跨界的完整问答，但原文读取不超过窗口条数。
3. 模型返回相关上下文 ID、无关或不确定。无关建立新段，相关恢复指定段。不确定、超时或格式错误时延续当前段。到 30 条时可提供最多 8 个旧段摘要作为恢复线索；不自动扫描整个原始历史。
4. 同段保留连续原文并逐轮追加。主请求最多 30 条消息，系统提示、工具定义、时间元数据、压缩摘要、图片估算均计入模型配置上下文的 50% 输入预算。当前工具轮次完整保留；超大当前轮次明确报错。
5. 回答或错误落盘后提交本轮引用，再异步生成摘要。摘要成功前仍可继续提问；摘要不会显示为聊天消息。

“一轮问答”是一个真实用户输入及其所有 assistant/tool 消息，工具读取图片产生的 `visual-*` 输入属于原轮次。原始历史和 UI 的分页加载不控制模型的上下文。

## 两种后台请求

两个任务使用固定 system prompt，每次都是新的无状态请求，只有当前所需材料，不追加各自过去的对话，也不携带主对话工具或时间提示。默认使用当前选中模型，不另设隐藏模型配置。

- **相关性**：`{"related":true|false|null,"context_id":"候选ID"|null,"need_more":true|false}`。代码验证 ID 和字段组合，禁止模型凭空指定上下文。超时 15 秒，输出上限 512 tokens。
- **摘要**：`{"summary":"..."}`。每轮非空摘要最多 200 个 Unicode 字符，标点、空格、数字均计入。格式或长度不合格时只重试一次，不截断成半句话；网络失败保留原文回退。最多一个摘要任务同时执行，下次提问补试一条未完成摘要，不批量补扫旧历史。超时 60 秒，输出上限 1,024 tokens。

固定 prompt 在 `context/prompts.rs`；明确区分实际完成、建议和失败，历史中的指令只作为数据。兼容 `<think>...</think>` 前缀和 JSON 代码围栏，截断/不合法 JSON 不作为成功结果。

后台输入另设 `min(模型上下文 × 50%, 12,000)` 的估算上限；长正文和工具参数按总量取首尾片段。每轮 200 字摘要是检索线索，不替代完整历史。

## 压缩与缓存

不在每次提问时移动历史起点。达到消息数或 token 上限才压缩一批完整旧问答，优先保留最近约 10 条原文，目标降到配置上下文约 25%，给后续追加留空间。使用已完成的问答摘要与有界原文，合并上一份压缩记录，生成最多 200 字的检查点。压缩失败保留原文并报错，不静默丢弃上下文。

检查点的内容和覆盖边界持久化后保持不变，直到下次达到上限。异步问答摘要完成时不重写检查点。相同话题的主请求保持系统提示、工具定义、检查点、旧消息顺序稳定；切换话题或压缩会改变相应前缀。历史时间提示来自消息固定时间戳。

Anthropic 请求对固定 system 和检查点添加 `cache_control`，主请求也启用自动缓存。OpenAI 兼容接口保留流式 usage 请求，由服务商决定缓存行为。新建独立请求不等于清除服务商前缀缓存；实际命中还受模型、最小缓存长度和有效期影响，不能保证每次命中或总费用必然下降。

## 存储与恢复

数据目录下新增 `context/state.json`，原子更新，包含：

- `turns`：问答标识、原始消息起止偏移、所属上下文、时间、完成状态、可选摘要。
- `segments`：隐藏上下文 ID、冻结的压缩摘要、覆盖到的问答起点、版本号。
- `active` / `observed`：当前段和已索引消息数。

原始聊天文件完全保留。重启后恢复段归属和检查点；旧安装首次仅导入最近 30 条范围内起点完整的问答，不为所有旧消息付费生成摘要。索引损坏或历史回退会明确报错，不覆盖损坏文件。用户可以备份后移走侧文件，从最近历史重新建立索引。

## 用量日志

每个 API 请求退出时打印一条 `[usage] {JSON}`，`stage` 区分 `main`、`relevance`、`summary`、`compact`，`question_id` 关联同一问题，`request_id` 区分工具轮次和尝试：

应用默认启用 usage 模块的 `info` 日志，其他模块仍为 `warn`，经现有 logger 输出到标准错误；显式设置 `RUST_LOG` 可以覆盖该过滤规则。

| 字段 | 含义 |
| --- | --- |
| `input_tokens` / `output_tokens` | API 返回的总输入 / 输出，输出包含厂商计入的推理 token |
| `total_tokens` | 已知输入 + 已知输出 |
| `cache_read_tokens` / `cache_write_tokens` | API 返回的缓存读取 / 创建数量 |
| `cache_hit_percent` | 缓存读取 ÷ 总输入 × 100；是 token 比例，不是请求命中率 |
| `uncached_input_tokens` | Anthropic 原始 `input_tokens`，不含缓存读取/创建 |
| `completed` / `elapsed_ms` | 流是否完整结束、请求耗时 |

OpenAI 兼容解析 `prompt_tokens_details.cached_tokens` 和 DeepSeek `prompt_cache_hit_tokens`。Anthropic 总输入由未缓存、缓存读取、缓存创建三部分相加；累计 delta 覆盖旧计数，不反复相加。

服务商未返回或中断时缺失的字段是 `null`，不会伪造成 0，也不会用本地估算冒充账单值。缓存读取是输入的子集，不能把两者再次相加。日志不输出 API Key、正文或摘要。现阶段不在 UI 展示统计。

## 验证

```bash
cargo test -p buddy-engine --lib --tests
cargo run -p buddy-engine --example context_usage
```

示例使用当前模型配置，在临时目录发起“解释 Rust 所有权”及“如何避免重复释放”的真实请求，等待摘要落盘，打印每阶段用量和第二问合计。会产生实际 API 费用；不会写入用户聊天记录，临时配置随目录清理。
