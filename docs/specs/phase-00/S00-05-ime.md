## 证据

### 0. 最重要的结论：官方示例自带 **4 个缺陷**，其中 2 个是「一碰输入法就崩」级

`crates/gpui/examples/input.rs` 是官方唯一的自建输入框参考，但实测发现：

| # | 位置 | 缺陷 | 后果 |
|---|------|------|------|
| 1 | `character_index_for_point` | 断言 `last_layout.text == self.content` 未考虑 placeholder | **一装输入法就崩** |
| 2 | `replace_and_mark_text_in_range` | `+ range.end` 应为 `+ range.start` | 光标越界 → 候选窗偏移 |
| 3 | `TextElement::prepaint` | 整段 content 一次 `shape_line` | **多行输入 panic** |
| 4 | `replace_and_mark_text_in_range` | UTF-16 区间算术产出越界 `selected_range` | **组字中 Cmd+C/X panic** |

**四个均非本项目引入。** 结论：**官方示例只能当骨架，不能当 IME / 多行正确性参考** ——
它显然只在「无 placeholder + 英文 + 单行」场景下被验证过。

> 这直接解释了 Comet 为何要写 8768 行 `composer.rs` —— 并非过度设计。

### 1. 缺陷 1 的实测：一启动就崩

```
thread 'main' panicked at src/main.rs:463:
assertion `left == right` failed
  left: "在这里用拼音输入法打字…"     ← placeholder
 right: ""                            ← content
```

调用链：macOS `characterIndexForPoint:` → `gpui_macos/src/window.rs:3420`
→ `InputHandler::character_index_for_point`。

**根因**：`prepaint` 在 `content.is_empty()` 时用 **placeholder** 作为 `display_text`
并把该布局存进 `last_layout`；而原断言拿它与 `self.content`（空串）比较。

**触发条件**：`characterIndexForPoint:` 是 **IME 定位组字位置的标准查询**，
所以**只要输入法激活并查询就必然命中**。

> 注意：换成英文 placeholder（原文 `"Type here..."`）**同样会崩** —— 与文案无关。

**修法**（保留断言意图，补上 placeholder 情形）：
```rust
debug_assert!(
    last_layout.text == self.content
        || (self.content.is_empty() && last_layout.text == self.placeholder),
    ...
);
```

### 2. 缺陷 2 的实测：光标全程越界

```
preedit="n"      marked=Some(0..1)  cursor=1   content="n"       ✓ len=1
preedit="ni"     marked=Some(0..2)  cursor=3   content="ni"      ✗ len=2
preedit="ni'h"   marked=Some(0..4)  cursor=6   content="ni'h"    ✗ len=4
preedit="ni'hao" marked=Some(0..6)  cursor=11  content="ni'hao"  ✗ len=6
```

`new_selected_range_utf16` 是**相对 `new_text`** 的偏移，两端都应加 `range.start`。
原代码两端加了不同的值（`+ range.start` / `+ range.end`），每轮组字多偏移
`range.end - range.start`。

**修法**：`.map(|new_range| range.start + new_range.start..range.start + new_range.end)`

**修后**：`cursor=1/len=1`、`2/len=2`、`4/len=4`、`5/len=5`、`6/len=6` —— 全程匹配。

### 3. 缺陷 3 的实测：多行直接 panic（**对 Buddy 最关键**）

```
panicked at gpui/src/text_system.rs:420:
text argument should not contain newlines
```

`TextSystem::shape_line` 的文档与 `debug_assert!` 明确写着：

> Note that this method can only shape a single line of text.
> **It will panic if the text contains newlines.**
> If you need to shape multiple lines of text, use `Self::shape_text` instead.

官方示例把**整段 content 一次性 `shape_line`** → **根本无法支持多行输入**。

**对 Buddy 的意义**：Composer 是多行的（Shift+Enter + 自动增高），
所以**不能照抄官方示例的渲染方式**。

**修法**（本 spike 采用）：按 `\n` 拆**逻辑行**，逐行 `shape_line` + 逐行 `paint`，
并记录每行在 content 中的起始字节偏移，用于光标 / 选区 / IME 坐标换算。
新增 `MultiLine` 结构承载（实现见产物文件）。

配套改动 4 处：
| 方法 | 改动 |
|------|------|
| `MultiLine::locate` / `x_of` | 字节偏移 ↔ (行, 行内偏移/x) |
| `MultiLine::offset_at` | 局部坐标 → 全局偏移（**IME 的 `characterIndexForPoint:` 入口**） |
| `bounds_for_range` | 多行版，返回 range 的屏幕矩形 —— **这正是 macOS 定位 IME 候选窗的锚点** |
| `index_for_mouse_position` | 多行鼠标点击定位 |
| 选区渲染 | 逐行绘制，支持跨行 |

**修后实测**：Shift+Enter 5 次，行数 2→6，**零 panic**。

### 4. 缺陷 4 的实测与防御

```
preedit="d" marked=Some(9..10) cursor=12/len=10  content="你好\n\n\nd"
```

`content` 长 10 字节而 `selected_range.end = 12`。

**危害**：`copy()` / `cut()` 执行 `self.content[self.selected_range.clone()]`
→ **切片越界 panic**（`copy` 只用 `is_empty()` 守卫，而组字期间非空）。

**为什么视觉上看不出来**：渲染层 `MultiLine::locate` 与 `bounds_for_range`
都做了 clamp —— 所以光标画在行尾、候选窗也正常，**用户不会察觉**，但语义层已错。

**修法**（防御性 clamp）：
```rust
let clamped_end = self.selected_range.end.min(self.content.len());
let clamped_start = self.selected_range.start.min(clamped_end);
self.selected_range = clamped_start..clamped_end;
```

**实测**：`Cmd+C`（组字中）不再崩溃；`光标仍越界` 日志 **0 次**。

> ⚠️ **上游根因未完全查清**：官方示例的 UTF-16 ↔ UTF-8 区间换算
> （`range_from_utf16` / `text_for_range` / `new_selected_range_utf16` 的语义）
> 存在不一致，本 spec 只做了防御性 clamp。**已交接 `S05-06` 重新核对坐标系语义。**

### 5. Enter 三态：**由 gpui 在平台层保证**（源码级确认 + 实测）

`gpui_macos/src/window.rs:2635-2695`：

```rust
// is_composing 直接来自我们实现的 marked_text_range()
let is_composing = input_handler.marked_text_range().flatten().is_some();

if is_composing || is_ime_printable_key || (…) {
    let handled: BOOL = msg_send![input_context, handleEvent: native_event];
    if let Some(h) = do_command_handled.take() { return h as BOOL; }
    else if handled == YES { return YES; }   // ← IME 已消费，不再走 keyDown 回调
    let handled = run_callback(PlatformInput::KeyDown(key_down_event));
    return handled;
}
```

**组字期间 Enter 被 `inputContext` 消费，不会到达应用的 action 处理器。**

**推论（重要）**：三态正确性的**前提**是应用正确实现 `marked_text_range()`——
若它返回 `None` 而实际正在组字，`is_composing` 为 false，Enter 会被当成普通按键 → **误发送**。
所以 `marked_text_range()` 必须与 `marked_range` 字段严格同步。

**实测**：

```
[ENTER] ✅ Enter → 发送（第 1 次）；content = "你好"
[ENTER] ✅ Shift+Enter → 换行（第 1 次）；行数 = 2
[ENTER] ✅ Shift+Enter → 换行（第 2 次）；行数 = 3
[ENTER] ✅ Shift+Enter → 换行（第 3 次）；行数 = 4
[ENTER] ✅ Enter → 发送（第 2 次）；content = "你好\n\n\ndsa"
...
[ENTER] ✅ Shift+Enter → 换行（第 5 次）；行数 = 6
```

**`组字期间收到了 Enter` = 0 次** ✅

## 决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 是否直接用官方示例 | **不直接用，改造后使用** | 官方示例有 4 个缺陷，其中 2 个致命。必须修后才可用 |
| 多行实现方案 | **按 `\n` 拆逻辑行 + 逐行 `shape_line`** | `shape_line` 拒绝 `\n`；`shape_text` 支持软换行但其索引 API 更复杂。Buddy 的 Composer 若允许逐行渲染，拆逻辑行已够用。**若要软换行则改用 `shape_text`** |
| Enter 三态实现 | **不在应用层做，依赖 gpui 平台层** | 源码确认 `inputContext handleEvent:` 返回 `YES` 时 gpui 会提前返回。前提是正确实现 `marked_text_range()` |
| 光标越界处理 | **防御性 clamp（渲染层 + 语义层都做）** | 渲染层 clamp 是必要的（否则视觉错乱）；语义层 clamp 是必要的（否则 `copy`/`cut` panic）。但**上游坐标系语义仍需在 `S05-06` 核对** |
| 证据形式 | **终端日志**而非录屏 | 逐条可复核、可 grep、可统计，比录屏更精确 |
| 是否 patch GPUI | **否** | 4 个缺陷都在**示例代码**里，不在 gpui 库内。gpui 的 IME 平台层实现是正确的 |
