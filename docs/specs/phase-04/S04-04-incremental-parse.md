## 目标

流式追加时只重解析最后一个未稳定的顶层块，解析放后台并合并在途请求（zed `markdown.rs` coalescing）。

## 输入

- zed `markdown.rs` 现有 append / parse 流程；Comet `crates/ui/src/markdown/parser.rs`（MIT）

## 实现要点

| ID | 事项 | 说明 |
|----|------|------|
| S04-04-1 | 先测后改 | 先测 zed 原生 append 在长文档下的耗时，达标则不改（YAGNI） —— **达标，不改** |

## 验收标准

- [x] 逐字喂入 5000 行文档，单次追加解析耗时有数值
- [x] 流式中无行尾重排 —— 渲染器与 S00-06 相同（用户已确认「行尾正常」）；本 spec 未改解析 / 渲染路径。完整流式观感随 S04-06 预览目检

## 证据

| 项 | 证据 |
|----|------|
| 上游机制 | `markdown.rs` `append` → `parse`：每次全量重解析，后台 `background_spawn`；在途时置 `should_reparse`，完成后再解析一轮（合并）。代码块高亮也在后台任务内（`markdown.rs:1375`），**计入测量** |
| 全量解析（release，两轮一致） | 200 行 1.3 ms（中位；首轮冷启动离群 24 ms）/ 1000 行 2.4–2.5 ms / **5000 行 9.0 ms**（max 9.7） |
| 流式（release） | 预灌 90% 后每 16ms 追加 48 字节：1000 行 40/40、**5000 行 199/199 次在一帧内追上**，额外延迟最大 **1.1 ms** |
| debug 对照 | 5000 行 45 ms；流式 0/199 一帧内追上、额外延迟 32 ms —— 说明决策须以 release 为准 |
| 测量方法 | `cargo run --release -p buddy-app --example markdown_preview -- --bench`；「追上」以 `!is_parsing()` 判定（合并语义保证其等价于解析到最新源文本；`parsed_markdown()` 仅 test-support 可见） |
| 提交 | `b919826` |

## 决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 增量解析 | **不做** | release 下 5000 行 9 ms、流式一帧内追上；引入 Comet 增量解析只增加复杂度与 vendored 改动 |
| 复评条件 | 若真实长会话出现卡顿 | S10-05 性能对比时用长会话样本复测 |
