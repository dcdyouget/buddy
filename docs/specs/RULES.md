# Spec 工作规则

> 本文件定义 v2.0.0-gpui 重构的 spec 驱动流程。**所有参与本重构的 agent 必须遵守。**
> 与 `docs/CONVENTIONS.md` 冲突时，编码规则以 CONVENTIONS 为准，流程规则以本文件为准。

---

## 1. 为什么用 spec

现有 `docs/tasks/v1.0.0/` 是「按阶段划分的任务清单」，粒度太粗：一个任务文件里塞了 6-20 个工作项，无法逐个标记完成，也无法判断「到底做完了没有」。

Spec 是**可独立实现、可独立验证、可独立标记完成**的最小交付单元。

---

## 2. Spec 粒度规则

一个 spec 必须满足全部四条：

1. **边界清晰** —— 产出物可以被一句话说清（「vendor 并 patch 掉 settings 耦合」而不是「做 markdown」）
2. **可独立验证** —— 有明确的验收标准，不需要等别的 spec 才能验证
3. **可独立完成** —— 一次专注工作内能实现并自测完，不需要跨多次会话
4. **不产生中间死亡态** —— 完成后不留下「必须等下一个 spec 才能跑」的半成品

**不合格的例子**：

| 反例 | 问题 |
|------|------|
| 「移植聊天界面」 | 太大，无法一次完成，无法验证 |
| 「把 D01-D36 都做了」 | 用编号代替边界，等于没拆 |
| 「重构 engine」 | 边界模糊 |
| 「写一个 helper 函数」 | 太小，且完成后无可验证价值 |

**参考粒度**：`docs/specs/README.md` 中列出的 105 个 spec 即为标准粒度。

---

## 3. 文件位置与命名

```
docs/specs/
├── RULES.md                    # 本文件
├── README.md                   # 注册表 + 进度板（唯一权威状态源）
├── _TEMPLATE.md                # spec 模板
├── design-deletions.md         # 设计文档退役台账
├── phase-00/
│   ├── S00-01-extract-theme-ui.md
│   └── ...
├── phase-01/
└── ...
```

- 目录：`phase-NN/`
- 文件名：`S<phase 两位>-<序号两位>-<短横线英文摘要>.md`
- Spec ID 一旦分配**永不复用**，即使 spec 被废弃

**ID 命名空间独占**：`S<NN>-<NN>` 格式的编号由 `docs/specs/` **独占**。
`docs/tasks/` 下的文件不得自建 `S01`、`S02` 这类编号（历史上 `00-spike.md` 曾使用，已清除）—— 它只能引用 spec ID，不能定义。
工作项素材使用 `D<NN>` / `T<NN>` 前缀，与 spec ID 不冲突。

---

## 4. Spec 状态机

| 状态 | 含义 |
|------|------|
| `todo` | 已定义，未开始 |
| `doing` | 进行中（同一时刻**最多 2 个** spec 处于 doing，避免并行失控） |
| `blocked` | 被阻塞，**必须写明阻塞在哪个 spec 或哪个未知** |
| `done` | 完成定义全部满足（见 §5） |
| `dropped` | 废弃，**必须写明废弃原因**并保留文件 |

状态写在**两处**，必须始终一致：

1. spec 文件头部的状态块
2. `docs/specs/README.md` 的注册表

### Spec 文件头部格式

```markdown
# S04-01 vendor zed markdown.rs 并 patch ThemeSettings

> 状态: `todo`
> Phase: 04
> 依赖: S01-02
> 阻塞: —
> 退役设计文档: `docs/design/rust-architecture.md` §markdown
```

---

## 5. 完成定义（Definition of Done）

一个 spec 只有在**全部满足**后才能标记 `done`：

- [ ] 验收标准每一条都已勾选，且**有证据**
- [ ] 证据已写入 spec 的「证据」段（见 §6）
- [ ] `docs/specs/README.md` 注册表状态已同步更新
- [ ] 设计文档处置已完成（见 §7）—— 该退役的已退役，该保留的已标注
- [ ] 若有决策产生，已写入 spec 的「决策记录」段
- [ ] 「完成记录」段填写了日期与 commit

> **不允许**只改状态不写证据。不允许写「OK」「已完成」这类无信息量的结论。

---

## 6. 证据要求

证据必须是**可复核的具体材料**，不接受主观判断：

| 类型 | 可接受的证据 |
|------|-------------|
| 编译/依赖 | `cargo tree` / `cargo check` 的输出片段（不是「编译通过」） |
| 行为 | 录屏、截图、操作步骤 + 观察结果 |
| 性能 | 具体数值（启动 ms、内存 MB、帧率） |
| 代码 | commit hash |
| 缺陷 | 「看似生效实则 no-op」的 API 必须写**探测方法**与**探测结果** |

**反面例子**：

> ❌ 「窗口行为正常」

**正面例子**：

> ✅ 「`WindowKind::Floating` 在 Windows 后端源码 0 次出现（`grep -c Floating crates/gpui_windows/src/window.rs` → 0）。实测：以 `Floating` 开窗后 `GetWindowLong(GWL_EXSTYLE)` 返回 `0x100`（WS_EX_WINDOWEDGE），无 `WS_EX_TOPMOST`(0x8)，证明未置顶。录屏 `evidence/s09-window-kind.mp4`」

## 7. 设计文档生命周期（核心规则）

### 7.1 原则

> **代码实现完设计文档之后，就删掉设计文档。代码即文档，不留冗余信息。**

设计文档是**脚手架**，不是永久资产。它的价值在实现完成的那一刻终止。

### 7.2 处置时机

每个 spec 在标记 `done` 之前，必须检查它涉及的**设计文档段落**是否已被完整实现：

| 情况 | 处置 |
|------|------|
| 该段落已被完整实现 | **删除该段落**；若整份文档所有段落都已实现，**删除整个文件** |
| 该段落部分实现 | 保留文件，在文件头标注「已实现：<spec 列表>」与「未实现：<剩余内容>」 |
| 该文档描述的能力已被整体移除（如 IPC 契约） | 直接删除，在台账中登记原因 |

### 7.3 删除前必须做的事：迁移「why」

**这是唯一的例外约束。** 代码能表达「做什么」（what），但表达不了「为什么这么决定」（why）。删除前必须检查并迁移：

| 内容类型 | 处置 |
|---------|------|
| 可自明的事实（布局、接口、字段） | 无需迁移，直接删 |
| 决策理由（为何选 A 不选 B） | 迁移到 spec 的「决策记录」段 |
| 跨模块的架构约束（如「窗口切页不改变尺寸」） | 迁移到代码注释 + `AGENTS.md` 硬约束 |
| 来自外部系统的兼容性要求（如「必须指向与旧版本相同的数据目录」） | 迁移到代码注释 |

> **判断标准**：如果半年后有人想改这段代码，光看代码会不会做出错误决定？会 → 必须先迁移 why。

### 7.4 登记台账

每次删除设计文档，必须在 `docs/specs/design-deletions.md` 登记：

| 文件/段落 | 删除日期 | 由哪些 spec 替代 | why 迁移去向 |
|----------|---------|-----------------|-------------|
| `docs/design/ipc-contract.md` | 2026-xx-xx | S02-08 | 不适用（能力被整体移除） |

**没有登记 = 删除无效。** 台账的作用是防止后人疑惑「文档去哪了」。

### 7.5 同步索引

删除设计文档后，**必须同步更新 `AGENTS.md` 的 Document Index 表**，移除对应行。索引与文件系统不一致视为缺陷。

### 7.6 现有设计文档的退役归属

**待退役清单只在 `docs/specs/design-deletions.md` 维护，本文件不重复。**

每个 spec 在文件头部的 `退役设计文档` 字段声明它负责退役的文档段落。Registry 汇总后即为完整台账。

> 在写 spec 的 `退役设计文档` 字段前，**必须先验证该路径真实存在**（见 §11）。

## 8. 与 tasks 目录的分工

| 目录 | 角色 |
|------|------|
| `docs/tasks/v2.0.0-gpui/` | **背景与拆解依据**：调研证据、Phase 划分、工作项来源。不承载状态 |
| `docs/specs/` | **执行与状态**：具体 spec、状态、证据、完成记录。**唯一权威状态源** |

Phase 文件中的工作项（D01、T01 等）是 spec 的**素材**，spec 是这些素材的实现载体。一个 spec 可以覆盖多个工作项，也可以只覆盖一个。

## 9. 推进纪律

1. **Phase 00 未通过禁止启动 Phase 01+**（见 `docs/tasks/v2.0.0-gpui/overview.md`）
2. **Phase 09 在 macOS 验收通过前不启动**
3. **不跳过 `todo` → `doing` → `done`**，不允许直接 `todo` → `done`
4. **`blocked` 必须写明阻塞对象**，不允许写「暂时无法推进」
5. 每个 Phase 启动时，从 `README.md` 展开该 Phase 的详细 spec 文件
6. 每完成一个 spec，**立即**更新注册表（不批量补记）

### 9.1 Phase 单调性不变式（强制）

> **Phase `NN` 的 spec 只能依赖 Phase ≤ `NN` 的 spec。**

禁止跨 Phase 前向依赖。若一个 spec 必须依赖后续 Phase 的产出，说明它放错了 Phase，应移到后面。

理由：前向依赖会让「Phase 准入条件」失去意义，并产生「本 Phase 所有 spec 做完却仍卡着」的状态。

**该不变式可用脚本校验**（见 §11 与 S01-04）。

### 9.2 准入条件的含义

注册表中的「准入条件」是**必要条件而非充分条件**。具体能否开始某个 spec，**以该 spec 自身的 `依赖` 字段为准**。

---

## 10. Spec 展开约定

`docs/specs/README.md` 注册表包含全部 spec 的完整拆解（105 个）。

**详细 spec 文件按 Phase 逐个展开**（对应「分段推进」）：Phase 启动时才创建该 Phase 的 `phase-NN/*.md`，避免为远期工作写会失效的细节。

当前已展开：Phase 00、Phase 01、Phase 02。

## 11. 文档卫生规则

本节规则来自一次实际审计发现的缺陷（`docs/design/prototypes/` 等路径被多份文档引用但**根本不存在**，且沿 `AGENTS.md` → `CLAUDE.md` → `docs/tasks/` 一路传播）。

### 11.1 路径引用必须验证

写文档时引用任何文件/目录路径，**必须先确认它存在**。

- 禁止基于「别的文档这么写」就沿用路径
- 禁止引用仅为规划、尚未创建的文件
- 若必须引用未来产物，明确标注「（待创建，由 Sxx-xx 产出）」

### 11.2 单一真相源

同一份信息**只能有一处权威维护**。其他地方一律用指针（链接 + 章节名）。

已确立的单一真相源：

| 信息 | 唯一维护处 |
|------|-----------|
| spec 状态与进度 | `docs/specs/README.md` |
| 设计文档退役台账 | `docs/specs/design-deletions.md` |
| 调研证据与风险登记 | `docs/tasks/v2.0.0-gpui/research-log.md` |
| 硬约束 | `AGENTS.md` |
| 编码规则 | `docs/CONVENTIONS.md` |
| 设计令牌真值 | `docs/design/design-tokens.md`（v1 视觉以 `src/styles/global.css` 为准） |
| 视觉与动效真值 | **代码本身**（v1: `src/styles/global.css`；v2: `crates/ui` 的 `Theme`） |

### 11.3 不改历史

`docs/tasks/v1.0.0/` 是历史记录，**修正其中错误的路径反而是错的**——它反映当时的真实状态。新文档不得沿用其中的路径，但不去改它。

### 11.4 禁止双入口文档（薄指针例外）

**禁止两份文档各自维护同一内容。** 曾经 `AGENTS.md` 与 `CLAUDE.md` 各持一份 Document Index 并已开始漂移。

**权威入口只有一个：`AGENTS.md`。**

#### 各 agent 的入口文件清单

各工具约定不同的入口文件名。它们**一律只能是薄指针**，不得包含独立内容：

| 工具 | 入口文件 | 状态 |
|------|---------|------|
| Codex / 通用 AGENTS 约定 | `AGENTS.md` | **权威** |
| Claude Code | `CLAUDE.md` | 薄指针 |
| Gemini CLI | `GEMINI.md` | 薄指针 |
| Cursor | `.cursor/rules/buddy.mdc` | 薄指针 |
| GitHub Copilot | `.github/copilot-instructions.md` | 薄指针 |
| Windsurf | `.windsurfrules` | 薄指针 |
| Cline / Roo Code | `.clinerules` | 薄指针 |
| Zed | `.rules` | 薄指针 |
| Aider | 直接读 `AGENTS.md`（新版支持），无需额外文件 | — |

#### 薄指针的允许与禁止

**允许**：指向 `AGENTS.md` 的链接、必读清单（文件路径 + 一句话用途）、三五条最容易犯的错。

**禁止**：任何 `AGENTS.md` / `CONVENTIONS.md` / `RULES.md` 已有的具体规则文本、接口定义、约束数值。

#### 新增一个 agent 入口时

1. 写薄指针，**不要写内容**
2. 在上表补一行
3. 修正 `S01-04` 的 CI 校验清单（确保能拦住本文件被写入实质内容）

#### 防漂移

所有薄指针必须包含对 `AGENTS.md` 的引用。CI 校验其**存在性与指向正确性**（见 S01-04-14），不校验内容——因为内容本就不应该存在。

## 12. 设计即代码

> **代码实现就是设计。不存在独立的「设计稿」产物。**

本节确立一条贯穿全项目的原则，与 §7（设计文档退役）同源：

| 不要做 | 应该做 |
|--------|--------|
| 另立设计稿 / 视觉稿 / 动效稿 | 直接改代码 |
| 用图或 HTML 原型作为视觉真值 | 看运行的 v1 应用，或看 `src/styles/global.css` |
| 为动效参数写一份独立文档 | 用 `global.css` 的 `--duration-*` / `--ease-*` 令牌（v2 为 `Theme`） |
| 把设计快照当成长期资产 | 需要时用 S01-06 的方式采集一次（仅作迁移期对照） |

### 唯一的例外

**S01-06 采集的 v1 基线截图**是必要例外：它不是设计稿，而是**迁移期的回归基准**，用于证明「重构没有把已有界面改坏」。它提交一次、不可再生，保留至 v2 验收完成。

### 判断标准

> 想要新建一份「设计」类文档前，先问：**这个信息能不能从代码里读出来？**
> 能 → 不要建文档，去读代码。
> 不能（如不可再生的基线快照、已删除产物的历史）→ 符合 §11.2 的单一真相源则建，否则不建。

## 13. 文档必须入库

> **本节源于一次严重审计发现**：`.gitignore` 曾有一行 `docs/**`，把整个文档体系排除在 git 之外（仓库里只有代码）。这导致 spec 注册表、证据、agent 入口均不入库，**克隆出来的仓库无法工作，CI 也无法校验文档**。

#### 强制要求

下列内容**必须被 git 跟踪**，不允许加入 `.gitignore`：

| 内容 | 理由 |
|------|------|
| `docs/specs/**` | spec 注册表是唯一状态源，CI 需读取 |
| `docs/evidence/**` | v1 基线等不可再生证据，丢失即无法验收 |
| `docs/CONVENTIONS.md` | 所有 agent 必须读 |
| `docs/tasks/**` | spec 的执行背景与拆解依据 |
| `docs/design/**` | 尚未退役的设计文档是实现输入 |
| `AGENTS.md` 与全部 agent 入口文件 | 否则其他 agent 无法接入 |
| `README.md` | 公开仓库的基本要求 |

#### 与设计文档退役规则的关系

文档入库**不**与 §7 的退役规则矛盾：

- 未实现的设计文档 → 入库（它是实现输入）
- 已实现的设计文档 → 删除并登记台账（删除本身也是一次入库的提交）
- 已退役的事实 → 保留在 `design-deletions.md`（入库）

#### 新增 `.gitignore` 规则时

任何排除 `docs/` 或 agent 入口文件的规则，都必须在 spec 的「决策记录」段写明理由，并通过 S01-04-15 的 CI 校验。
